Inside the Arbiter

The decision engine that owns every notification. It never edits anything — on each run it erases its world and rebuilds it from data, so a notification exists only while the data justifies it.

1.0The loop — erase, rebuild, defend, choose

Anything that changes the data calls reevaluate(reason:). Time-based triggers (app open, background wake) are debounced 60 seconds; data changes always run. The run itself is five steps, always in the same order.

2.0The gates — four questions, asked about the fire moment

A candidate that survives building must pass four checks — and every one asks about the candidate's fire date, never about right now. A gate keyed on "now" silently kills tomorrow's nudge because of something happening this minute; that bug shipped twice before the rule was made absolute.

3.0Winner selection — facts are seeded, suggestions compete

Survivors don't all get scheduled. Exempt candidates are seeded into the winner set first; then discretionary candidates fill in under a daily budget of 10 and a minimum spacing of 90 minutes. That ordering has a visible consequence: a suggestion too close to an event's reminder loses its slot to it.

4.0After the nudge — every notification leaves a record

Scheduling writes a pending outcome row. What happens to that row depends on the user — and on time. This is the system's memory: today it only records; the fatigue gate that would consume it is deliberately off until enough baseline data exists.

Why the fatigue gate stays off: the arbiter is being run in record-only mode until enough outcome rows exist per kind to tune against. Arming consumption before the baseline exists would suppress exactly the signals being measured — the floater check-in has produced almost no rows yet, and it is the kind stakes-weighting would penalize first.
