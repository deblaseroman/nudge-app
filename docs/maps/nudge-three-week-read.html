The Three-Week Read

Roman's proposal, drawn as a mechanism: the store holds the whole calendar, an AI reader looks three weeks ahead, and the window rolls a week at a time so the app prepares the user for what is coming. Nothing here is built.

1.0Two windows where there was one

Today one number, 21, does two jobs: it is how far the import fetches and, by accident, how far anything can see. The proposal separates them. The import window becomes the whole calendar, or a long cap, so the store knows about the final exam in week six. The reading window is a separate three-week span the AI reader looks at, and it is the only part that spends tokens.

2.0What the reader sees, and what it is allowed to say

The reader generalizes what the exam sweep already does. Today "exam" is the one word that earns lead-up tasks. The reader decides prep-worthiness by judgment across the window, then hands back a shape the sweep already knows how to write: one parent event, a lead in days, and a list of small titled tasks placed on days before it.

3.0How the window rolls, and when the reader runs

Roman's cadence: read three weeks, and when a week completes, read one more week ahead. Drawn out, that is a window that slides one week at a time, so every event is read at least twice before it arrives (once entering week three, once more as it moves in), and a change inside the window is caught within a day.

4.0What a read costs

One call per read. The input is the window's events and open tasks, pre-phrased the way the memo's context is, so the model never does date math. A busy student calendar is the sizing case: roughly 60 events and 20 tasks in three weeks. The model is Roman's decision (5.0); the table shows the same read on each candidate.

5.0Decisions this needs before it is a plan

Amber entries are Roman's to make. Blue is a recommendation offered with the reasoning, to accept or overrule. Green is already settled by DESIGN.md or existing code.

  • Import cap. ROMAN
    Whole calendar, or a cap such as 180 days? A recurring class imports one row per occurrence, so a year of a 3×/week class is ~150 rows. Nothing downstream is unbounded (every reader has a fetch limit), so the cost of "everything" is store size and the purge, not tokens.
  • Which model reads. ROMAN
    Section 4.0. Per the cost-discipline rule this is a per-call-site choice; the Sep 14 bake-off suggests Sonnet holds on structured judgment. Opus keeps one tier for every "thinks about the user's data" call.
  • What counts as prep-worthy, and who decides. ROMAN
    Pure model judgment, or a keyword floor (exam, interview, flight, presentation, move) the model may extend? A floor keeps the exam path exactly deterministic and lets the reader add kinds; pure judgment is simpler and can miss or over-reach.
  • Lead per kind. ROMAN
    Exams use 3 / 7 / 14 today. Trips, interviews, and the rest need their own coarse bands, or the reader picks within a cap. Coarse bands only, as the capture rule already says: no invented precision.
  • The reader proposes; the sweep writes. RECOMMENDED
    Keeps the AI out of the write path and reuses idempotence, tombstones, the user-task dedupe, and the message-box announcement. The alternative, letting the reader write tasks directly, duplicates all four and puts a second capture bug surface in the app.
  • Exams stay deterministic; the reader adds the other kinds. RECOMMENDED
    The exam sweep is the defining feature and works offline. Let the reader cover everything except exam-category events, or let it propose for exams too and have the sweep ignore proposals for events it already handles. Either way the offline fallback is today's behavior, unchanged.
  • What the user sees. RECOMMENDED
    The message-box announcement, as the exam sweep does today ("Your trip is in 4 days, I've added two small tasks"). The memo already narrates upcoming events and can name the prep. No new surface, no new notification kind.
  • No API call in the arbiter's path. SETTLED
    DESIGN.md. The reader runs in the day-change chain where the exam sweep runs, before the arbiter, and writes only through the sweep. Notification timing stays reproducible from local data.
  • The iCal feed joins the daily refresh. FOLLOWS
    A whole-calendar store is meaningless if the Canvas feed is a one-time snapshot. The persisted feed URL already exists; the refresh only needs to re-fetch it on the cadence Apple Calendar already uses. Deterministic, free.
