1.0System context — one store, one decision engine

Everything flows through a single shared SwiftData store. AI turns language into structure on the way in; everything downstream of the store — planning, notification decisions — is deterministic. The store is also where the loop closes: every notification's outcome is written back as data the system can learn from.

2.0The scheduling model — four independent facts about a task

A task carries up to four scheduling facts, and they are deliberately independent fields with exclusive consumers. The load-bearing rule: a deadline is work that is owed; an intent day is a day the user chose. Only deadlines may generate time pressure — an intention can never produce a countdown, an overdue state, or a "due soon" nudge.

3.0The arbiter — a declarative rebuild, not a scheduler

On every trigger the arbiter cancels everything it owns and rebuilds the world from data. Nothing is ever "updated" — a notification exists only if the current data justifies it. Two lanes exist: discretionary nudges pass shared gates and compete for budget; factual reminders (an event is about to start) bypass the gates, self-checking only what applies to them.

4.0Process boundaries — two executables, one truth

The app and the widget are separate processes that must agree about the data. They share one store and one settings suite through an App Group — but the widget builds its own model container, and the code they share crosses the boundary through a hand-maintained list, not automatically.

5.0Where AI is allowed — and how much it costs

Seven live call sites, tiered per site: the one place where judgment is the product runs the frontier model; high-volume background jobs run the cheap one. The arbiter itself calls no model — AI-derived data reaches it only as cached fields read synchronously.

6.0Standing rules — the tripwires

Each of these exists because its violation shipped a real bug. They are the part of the map that must never drift.

  • UI never schedules notifications. Views mutate data and call reevaluate. The arbiter is the only scheduling site.
  • Every gate reads the candidate's fire date, never now. A now-keyed gate silently deletes future candidates because of something happening this minute.
  • One outcome kind per feature. Two builders sharing a kind produce rows nobody can attribute — the ability to measure either is silently lost.
  • Three schema lists, synced by hand. App, widget, and preview containers each declare the models; a miss is a runtime crash.
  • Deadlines are owed; intents are chosen. Only dueDate/specificTime may produce countdowns, overdue states, or dueSoon nudges. When capture is unsure, it guesses intent — the cheap failure.
  • Stakes is recorded, not consumed. The scorer accepts it; no production caller passes it. Arming waits for floater baseline data.
  • Every tunable lives in NudgeConfig. Behavior changes there, never as inline constants.
  • Arbiter changes get a before/after dump on real data first. The debug*Impact seams exist for this; they have caught wrong assumptions repeatedly.
