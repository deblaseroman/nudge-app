## 1 — Split get-ahead into `prep` and `dueSoon`

One builder currently serves two jobs and does neither well. Split into two
kinds:

**`prep`** — "start early." Fires days ahead via `StartByPlanner`'s
existing day math, anchored at the wake+2h hour (already fixed). Escalates
nothing; one per task per day at most. Discretionary: counts against
budget, respects quiet hours, spacing, fatigue (when armed).

**`dueSoon`** — "this is landing." Fires ~2 hours before a deadline, once
per task. Factual, low-pressure copy. **Budget-exempt** like event blocks —
a deadline is a fact, not a suggestion — and **structurally exempt from the
fatigue gate** (`successIsObservableInApp` reasoning: the success case is
handling the thing, which may not touch the app). But it must NOT skip the
same-hour batching below.

**Batching:** several tasks due within the same hour produce **one**
notification — "3 things due by 11:59 PM: A, B, and C" — reusing the event
clustering pattern. Per-task banners bypassing spacing is the swipe-dismiss
training we designed against.

Migration notes: `.getAhead` outcome rows keep their raw value — additive
kinds only, note the cut date for anyone reading kind-level baselines. The
floater's action set stays its own. New kinds need entries everywhere
`NudgeOutcomeKind` is matched; the compiler finds exhaustive switches, grep
for the filters.

Quiet hours and a 4 AM deadline: dueSoon fires at 2 AM. Accept it — it's
budget-exempt and factual. Note it in the report so it's a recorded
decision, not an accident.

## 2 — Stop conflating body-taps with starting work

A notification body tap records `.tappedStart` for every kind —
indistinguishable in the data from actually starting a session. "Acted on
this" and "opened the app to see what it was" must be different values
before the fatigue gate ever arms.

Add a `.tappedOpen` result (or equivalent — name it well) written by the
default-action path; reserve `.tappedStart` for the explicit Start action.
The classifier's `.acted` inference and any consumer that matches
`tappedStart` need review — report each decision. Additive; old rows keep
their meaning, note the cut date.

## 3 — The morning prompt says when the named task is overdue

Last device pass: it named "Psych reading," due the previous day, with no
deadline clause at all. Dropping the clause was designed to avoid an
accusation before the user is out of bed — but total silence about
lateness hides a fact the user needs.

Add a neutral marker: `— was due yesterday` / `— was due Tue`. Factual,
past tense, no verdict. `DESIGN.md`'s honest-about-the-situation rule is
the spec here: state the fact, never the judgment. Extend the copy harness
cases to cover it.

## 4 — Study tasks from exam events (the core feature)

The prerequisite landed: `inferCategory` can now emit "exam" for imports.
Build the first version of the app's defining feature.

**Classifier:** add `prepLeadDays` to the brain-dump AND import
classification output — coarse bands only (3, 7, or 14), from the exam
title. Course level and subject carry the signal; the model already knows
organic chemistry outranks intro marketing. **No web search. No invented
precision.** Missing/invalid → default 7. Same tolerant decoding as every
other field.

**Detection sweep:** on launch and day-change (beside the placement
rollover), find exam-category events whose date is within `prepLeadDays`
of today and which have no prep task yet.

**Creation:** one study task per remaining day up to the exam day,
`source = "prep"` (the comment in the code already prescribes it), titled
plainly ("Study for <exam>"), linked to the exam event, stakes inherited
high, duration from the category prior. **Idempotent** — running the sweep
twice creates nothing new. **Capped** — never more than one per exam per
day, and if an exam is 3 days out, 3 tasks, not 14.

**Dedupe:** if the user already made their own study task for that exam,
create nothing. First version: deterministic matching — normalized title
containing the exam's course token or "study"+subject overlap. Report its
misses honestly; AI-based matching is a later cycle, don't build it now.

**Deletion tombstone:** if the user deletes a prep task, record it (the
deletion record must survive the task's removal — say where it lives,
mindful of the three schema lists if it's a new @Model). The sweep never
recreates a tombstoned day. Instead, the **message box** gets a sixth
state: a one-time note asking whether they still want study time for that
exam — factual, no guilt. Consuming that state clears it; it never
repeats.

**Announcement:** when the sweep creates tasks, the message box announces
it — "Your Stats exam is in 6 days — I've added study time each day until
then." That's what the box was built for. Wire it as a composer state
above resting, below overdue.

**What prep tasks feed:** they're ordinary tasks — the morning prompt can
name them, `prep` nudges fire on them, the planner places them. That's the
point: the exam stops being invisible to every surface that ranks tasks.

**Before/after per work-order item 5:** a DEBUG dump showing, for each
exam event: lead band, days remaining, tasks that would be / were created,
dedupe verdict, tombstone state. Run it in the report against fixture
exams at 2, 6, and 20 days out, plus one with a pre-existing user study
task and one with a tombstone.
