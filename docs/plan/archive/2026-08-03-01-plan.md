## The case

A brain dump says: *"three things by Friday. My python course, module 4.
Testing my app, an hour a day. Applying to three jobs a day with follow-up
emails."*

Today that produces three tasks with a Friday due date. It should produce a
week.

Three distinct shapes, and they need different handling:

- **Split work** — "module 4" is a finite body of work with a deadline. The
  app doesn't know how big it is.
- **A rate** — "an hour a day" states the cadence. Nothing needs dividing;
  it needs an end date to be finite.
- **A quantity per day** — "three jobs a day" is a count within a day, not
  a duration.

---

## 1 — Ask for what can't be inferred

Two questions, and **only** these two. This app's core research finding is
that planning apps fail by demanding effort up front; an interrogation
after a brain dump is that failure.

- **Split work with no effort estimate:** ask how long the user thinks it
  will take. "Roughly how many hours is Module 4?"
- **A rate with no end date:** ask when it ends. A rate without one is
  infinite.

**Remember the answers.** A second module of the same course should not ask
again — reuse `CategoryDurationStats`' learning pattern if it fits, and say
whether it did.

**Do not ask anything else.** Not the course name, not the platform. A
question that doesn't change what the app does costs the user attention and
returns nothing.

Where the question is asked is your call — the capture flow or the message
box. Say which and why. The message box exists to let the app speak and may
be the better home.

## 2 — Expand a commitment into daily tasks

Once the shape and the numbers are known, generate one task per day between
now and the deadline.

- **Split work:** total effort ÷ days available, rounded to sensible block
  lengths. Eight hours across four days is four two-hour sessions, not
  eight scattered fragments.
- **Rate:** one task per day at the stated duration.
- Same properties as prep tasks — linked to the parent commitment, stakes
  inherited, `source` marking them as generated.
- **Idempotent.** Running twice creates nothing new.
- **Deletion is tombstoned**, exactly as prep deletions are. Never silently
  regenerate; the message box asks once whether the user still wants it.

`ExamPrepSweep` already does the daily-generation, dedupe, tombstone, and
announce work. **Generalise it rather than duplicating it** if the shapes
allow — an exam is a commitment whose deadline is an event and whose work
is studying.

## 3 — Quantity-per-day tasks

"Three applications" is one task with a count, not three tasks. The model
has no notion of partial completion.

- Add a target count and a completed count to `NudgeTask` (additive,
  nullable — a normal task has neither).
- **Under four: render one checkbox per unit.** Three boxes, tap each.
- **Four or more: one checkbox with a number** that increments per tap
  until it reaches the target.
- The task does not complete until the count is met.
- Row treatment in `NudgeTheme`; no new colors.

**Carry-over, capped at three days.** Miss a day and the shortfall adds to
the next. **The carried amount stops growing after three days' worth** —
so a full week of misses shows the same number as three days of misses.

This cap is not a detail. An uncapped carry produces a number the user
cannot hit, and a number you cannot hit is the reason not to start.
`DESIGN.md`: never shame, and never show a target that has become
impossible.

Say how you're storing the carry, and make sure the *displayed* number is
always the capped one.

## 4 — Displacement when a day is full

A generated session needs a slot on a day with no room. The planner should
consider displacing a lower-stakes placed task.

**Only displace when it actually helps.** The common case is a two-hour
session and a day with two 45-minute gaps — evicting the least important
task there produces a slightly bigger fragment, not a two-hour slot. So:
displace only if doing so creates a gap the session genuinely fits in.
Otherwise leave the day alone and say it's full.

- **A displaced task returns to Unscheduled.** Visible, re-placeable, not
  silently moved to another day.
- **If candidates for displacement are equal in stakes, displace nothing.**
  Tell the user in the message box that the day is full and let them
  choose. `DESIGN.md`: the app proposes; the user decides.
- Never displace an event. Never displace a manual placement
  (`plannedIsAuto == false`).

## Evidence it worked

- Both schemes build after every commit.
- The brain dump above produces: a question about Module 4's size, a
  question about the app-testing end date, and once answered, daily tasks
  across the week.
- Eight hours across four days is four two-hour sessions.
- A three-count task shows three checkboxes; a ten-count shows a counter.
- Missing three days does not produce a fourth day's worth of carry.
- A displaced task appears in Unscheduled.
- Equal-stakes contention produces a message, not an eviction.
