## Why this exists

The app has one way to store a day: `dueDate`, and the entire system reads it
as a deadline. Capture dates everything the user mentions with a day — so
"study Python for an hour at 7" became *an assignment due at 7*. One
conflation, five symptoms:

- A countdown ("12 hours left") on tasks that aren't due — Roman's complaint.
- Fake overdue states on things that were never due, polluting the Overdue tab
  and the overdue-red row treatment.
- `dueSoon` notifications fire on fabricated deadlines ("this is landing" for
  a study hour). Roman has no real deadlines, so nearly every deadline-keyed
  nudge is built on invented data — most of why notifications feel ignorable.
- `EisenhowerScorer` urgency is a function of slack-to-deadline; fake
  deadlines produce fake urgency, which feeds idle/floater winner selection.
- The floater starves: it targets `dueDate == nil` open tasks, and since
  capture dates everything, `floater: SKIP — no open undated task` on every
  run. The floater baseline that blocks arming stakes can't accumulate.

The fix is the category, not the instance: **the schema learns the difference
between "this is DUE" and "I mean to do this then," capture stops writing
deadlines it wasn't told, and everything deadline-keyed reads only real
deadlines.**

### Design decision (made, but stated so it can be challenged)

Three candidate shapes were considered:

1. **A flag on dueDate** (`isHardDeadline: Bool`) — rejected: every read site
   keeps one field meaning two things and must remember to check the flag;
   forgetting reproduces this bug forever.
2. **Reuse `plannedStartDate` alone for intent** — rejected: placements are
   *timed slots* that `PlacementRollover` deliberately clears when the day
   passes. A day-only intention ("laundry on Saturday") has no time, and an
   intention should *survive* its day passing (it slipped; the slip is
   information) while a placement should not.
3. **A new `intendedDate: Date?` field** (day granularity, normalized to
   startOfDay) — chosen. Deadline = `dueDate`/`specificTime`, exactly as
   today, now meaning only real deadlines. Intent-day = `intendedDate`.
   Timed intent additionally becomes a manual placement (`plannedStartDate`),
   which the timeline, planners, and placement nudges already understand.
   When the day passes, `PlacementRollover` clears the placement as designed
   and `intendedDate` remains as the record of the slip.

`intendedDate` is a FIELD on `NudgeTask`, not a new `@Model` — the three
hand-synced schema lists do not change; SwiftData adds a nullable column with
no migration.

## Item 1 — Schema: `intendedDate`

`NudgeTask` gains `intendedDate: Date?` with a doc comment stating the rule:
*a day the user means to do the work; never a deadline; day granularity;
survives the day passing.* Add a convenience `var hasDeadline: Bool`
(`dueDate != nil || specificTime != nil`) so read sites express the split in
one word instead of re-deriving it.

No behavior change in this commit — the field exists, nothing writes it.

## Item 2 — Capture distinguishes DUE from START

Prompt (`chatSystemPrompt`):
- The `new_tasks` schema gains `"dueKind": "deadline" | "start"`, REQUIRED
  whenever `dueDate` is set on a task (events unaffected — an event's time is
  its time).
- The rule, stated as a category: **"due", "deadline", "submit", "closes",
  "turn in", exam/assignment context → `deadline`. "I'll", "I want to",
  "study at", "work on X at 7", plan items with times, chores given a day →
  `start`.** A date is when the user will DO it unless the message says it's
  when the work is OWED.
- The floater rule is untouched: no day mentioned at all → both null.

Write site (`HomeTabView`):
- `deadline` → `dueDate`/`dueTime`/`specificTime`, exactly as today.
- `start` → `intendedDate` = the stated day; if a clock time was stated,
  ALSO `plannedStartDate` at that time with `plannedIsAuto = false` — the
  user scheduling it themselves is a manual placement. `dueDate` stays nil.
- Missing/unknown `dueKind` with a date present → treat as `start`. The
  failure mode of guessing "start" is a task without a countdown; the failure
  mode of guessing "deadline" is this entire bug class. Default to the cheap
  failure.

**Consequence to verify, not fear:** placement nudges (`placementLead`,
`placementMissed`) already fire for any `plannedStartDate`. A captured
"study at 7" now gets a 5-minute heads-up and a follow-up if unstarted —
which is the notification Roman described wanting (needle-passes-task). This
is an arbiter-visible change; see Evidence.

## Item 3 — Read sites honor the split

- **Row display:** a task with `intendedDate` and no deadline shows a muted
  day label ("Tomorrow", "Sat") on the row's right side — the day isn't lost,
  it just carries no urgency: no countdown, no coral, no overdue treatment
  (the latter two are already impossible once `dueDate` is nil; the label is
  the only new UI).
- **Floater targeting:** targets tasks with **no deadline AND no
  today-or-future `intendedDate`** — a task intended for Friday isn't
  "whenever" work before Friday, but once Friday passes unstarted it is
  (the slipped intent is exactly what a check-in is for). This is the change
  that lets the floater population exist at all.
- **DayPlanEngine:** tasks with `intendedDate` == today become must-place
  candidates, after `sequenceIndex` plan tasks and ahead of score-ranked
  fill. The user said "today"; the planner's job is placing it, not
  re-deciding it.

`docs/plan/CONTEXT.md` census: the floater row's targeting rule and the
capture site description change **in the same commit** as this item, per
CLAUDE.md. The not-armed floater sentence updates too — this cycle is the
population fix it was waiting on.

## Item 4 — Existing rows: dry-run dump, hand fix, no auto-migration

Every existing dated task has a fabricated deadline. A DEBUG-only dump on
launch lists each open dated task with a proposed classification
(deadline-ish vs intent-ish, by category + title keywords) and writes
NOTHING. Roman reviews the printout and fixes rows by hand in the editor
(the store is one user's handful of rows), or a later cycle applies the
classification after he approves the printed table. Automated rewriting of
user data on a heuristic is how the last three category bugs happened; not
doing that here.

## Constraints

- No tab changes. Day-based organization (the Tomorrow request) is the NEXT
  cycle and reads `intendedDate`; it is not this cycle.
- Events untouched: `isInformationalEvent` rows keep `specificTime` semantics
  everywhere, and events never gain `intendedDate` or `dueKind`.
- Stakes stays unarmed (CLAUDE.md items 1–2). This cycle *creates* the
  floater population; baseline data still has to accumulate before anything
  arms.
- `DESIGN.md` / `ROADMAP.md` are Roman's; do not edit.
- Work-order item 5 applies: items 2 and 3 change what the arbiter sees
  (placements from capture; floater targeting). DEBUG before/after
  reevaluation dump on the real store before calling it done.

## Evidence it worked

- Re-dump the canonical case: "study python for an hour tomorrow at 7" →
  task with `estimatedMinutes` 60, `intendedDate` tomorrow, placement at
  7pm, **no dueDate** — row shows "Tomorrow", no countdown, can never go
  overdue-red. "essay due Friday 11:59pm" → deadline exactly as today, with
  countdown and dueSoon eligibility.
- Arbiter before/after dump on the real store: `floater:` line stops saying
  SKIP once a true floater or slipped intent exists; `dueSoon` candidates
  drop to only real deadlines; placement candidates appear for captured
  timed intents.
- The item-4 dump prints a classification table and writes nothing —
  verified by re-launching and seeing identical store contents.
